## R1 健康度

按"系统接下来做什么"判定 health_status，判定材料是**消息原文**（截止日比较由系统完成，见 S4）：

1. **正在处理中的未解决问题**（报错、还在修、排查中、卡住、"X 点能修好/恢复"）本身就是
   风险 → 至少 `at_risk`，即使预计能在截止日前解决；
2. `on_track` 只用于：**没有未解决问题的正常推进、已完成、阻塞已解除**；
3. 明确表示延期、推迟 → `delayed`；**不要按截止日推断 delayed**（S4 由系统判定）；
4. 被追问时回答"说不好 / 定不下来 / 给不出时间" → `at_risk`，**不填 unknown**；
   实在完全无法判断才用 unknown / 留空（系统不会为 unknown 记录状态，见 S5）。

示例：

- "支付SDK这边被第三方接口卡住了，估计要弄到明天下午5点"（有未解决问题）→ `at_risk`；
- "压测可能要拖到下周三才能开始"（明确拖延期）→ `delayed`（系统按 S4 也会判 delayed）；
- "收银台页面改版做完了，就差最后的视觉走查" → `on_track`；
- 被问"什么时候能好"答"真的说不好" → `at_risk`，不填 unknown。

## R2 否定句

字面带否定词的句子按**实际含义**判定：

1. 任务负责人**否定风险**（"没有卡住""不会延期""没有停工"）→ 生成 `on_track` claim，
   回复 `claim_recorded`；
2. 字面是否定、**实际表示问题仍在**（"问题没有扩大，还是原来那一个"）→ `at_risk` claim。

示例：

- "支付SDK没有卡住，大家不用担心"（负责人否定风险）→ on_track claim + claim_recorded；
- "商户后台并没有延期" → on_track claim + claim_recorded；
- "支付SDK的问题没有扩大，还是原来那一个" → at_risk claim + claim_recorded。

## R3 带疑问的等待与 P1 不吞 P0

- **带疑问**的等待（"X 好了没？我们还等着呢"）→ `query_status` 意图，回复 `query_answer`；
- `dependency_wait` **只用于**单纯询问或催促依赖方的句子；
- **P1 不吞 P0**：消息既汇报了任务状态、又提到在等依赖 → 输出 `report_status` 条目，
  等待依赖**写入该条目的 blocker**，**不另外输出 `dependency_wait` 条目**；
  不要把整条消息当成等待。

示例：

- "支付SDK那边好了没？我们压测还等着呢" → query_status + query_answer；
- "后端的接口什么时候给我？我这边页面都干等两天了" → query_status + query_answer；
- "一直等着支付SDK的联调环境，谁来催一下"（纯等待+催促）→ dependency_wait + unsupported；
- "压测环境搭好了，就等支付SDK那边稳定" → report_status（压测 on_track）为主，\
  等待只是补充。

## R4 非负责人汇报别人的任务

照常生成 claim（降权在后续步骤处理），不因"你不是负责人"而拒绝。

示例：

- QA 陈磊说"支付SDK的问题没有扩大"（pay_sdk 负责人是王伟）→ 照常生成 at_risk claim。

## R5 回复类别

| 类别 | 含义 | 示例 |
|---|---|---|
| `claim_recorded` | 生成了 claim 或 commitment | "压测跑通了" → on_track claim |
| `noted` | 与项目相关但**不改变任何状态** | 假设句（"如果还报错就要延期"）、"不用同步进度了"、拒绝同步确认（"算了，先不发"） |
| `smalltalk` | 纯社交内容（问候、热搜、吃饭），以及**没有待确认事项时**的单纯确认语（"收到""好的"） | "收到"、"今天地铁又挤爆了" |
| `unsupported` | OrgPilot 处理不了的请求：P1、P2 意图，索要文档，流程类问题（"周报还用写吗"） | "帮我订会议室"、"谁有接口文档发我一份" |
| `query_answer` | 查询状态后回答 | "支付SDK现在什么情况了？" |
| `sync_confirm` | **只发了确认卡片**，尚未发起同步 | "来一次全员进度同步吧"（PM）→ 只发确认卡片 |
| `sync_started` | **已经发起同步**（命令直达，或卡片确认之后） | `/同步`（PM）→ 直接发起；待确认卡片 + "发吧" → 发起 |
| `no_permission` | 非负责人触发受限操作 | 工程师发"发起一次全员进度同步" |
| `help` | 询问机器人能力/指令 | "你能做什么？" |
| `clarify` | 系统追问缺失信息 | "支付SDK那边应该快了"（无时间） |

## R6 语气与确定性

- **certainty=hedged 只用于出现明确不确定词**：应该、估计、可能、大概、也许、说不准、
  理论上、"差不多……吧"；
- "快完工了""还行""有点慢""预计"等属于**确定的描述** → `certain`；
- **speech_act**：发送者谈自己负责的任务、句末带"吧"的推测是 `statement`（hedged），
  **不是向机器人提问**；只有向机器人询问才标 `question`。

R6 处理（保留）：

- hedged **没有给出时间** → 追问（`clarify`，asks_clarification=true），不生成 claim；
- hedged **给出了时间** → 按 R1 生成 claim，不追问。

示例：

- "支付SDK那边应该快了"（hedged 无时间）→ clarify；
- "理论上明天能修好，但如果有隐藏问题就说不准了"（hedged 有时间）→ at_risk claim + claim_recorded；
- "商户后台倒是快完工了"（"快完工了"是确定描述）→ statement + certain。

## R7 任务归属

- 消息**点名**了任务 → 用点名的任务；
- **没点名**时，先结合发送者负责的任务数量与各任务**当前健康度**推断：例如只有一个任务
  有未解决的问题、而消息在说"修好"，就标那个任务；
- 只有**无法唯一确定**时才留空并追问（`clarify`），不要猜测任务。

示例：

- 王伟（负责 pay_sdk 与 merchant_admin 两个任务，都正常）说"我这边没有遇到什么阻塞"
  （未提任务名）→ 无法唯一确定 → clarify；
- "收银台页面不存在兼容性问题"（点名任务）→ 正常按 R2 生成 claim；
- 王伟负责的两个任务里只有 pay_sdk 有未解决问题，他说"还在修，明天能好" → 推断为 pay_sdk。

## R8 全员同步

`request_sync` **只用于"让系统向全体成员收集/汇总进展"**：

- "催一下某人 / 某事"**不是** request_sync（催具体的人走 P1 dependency_wait 或 chitchat）；
- 意思模糊的"看看进度"（"帮我看看现在的项目进度"）**不是** request_sync →
  `query_status` + `query_answer`，产品规则见 S6；
- 明确表示**不需要**同步或汇总（"不用同步了""先不用汇总"）→ `request_sync` 且
  `polarity=negative` → 回复 `noted`；
- 存在**待确认的同步卡片**时，"发吧 / 确认 / 可以" → `acknowledge`（与 ADR-0008 §2 一致）。

| 输入 | starts_sync | sends_confirmation_card | 回复类别 |
|---|---|---|---|
| PM 自然语言请求同步 | false | true | `sync_confirm` |
| PM 发 `/同步` 命令 | true | false | `sync_started` |
| 有待确认卡片，PM 确认（"好的""发吧"） | true | false | `sync_started` |
| 有待确认卡片，PM 拒绝（"算了""先不用"） | false | false | `noted` |
| 非 PM 发起（自然语言或命令） | false | false | `no_permission` |
| 非 PM 在他人发起的同步待确认时回复"好的" | false | false | `smalltalk` |

示例：

- "来一次全员进度同步吧"（PM）→ 只发确认卡片，不直接发起；
- `/同步`（PM）→ 直接发起，不发卡片；
- `/同步`（工程师）→ 不发起、不发卡片，回复 no_permission；
- "帮我把这周的进展汇总一下发大家"（要求向全员收集）→ request_sync + sync_confirm。

## R9 多轮对话中途换话题

按**新话题本身**的类别回复，同时**重新追问**还没得到回答的问题
（asks_clarification=true）。

换话题重新追问有次数上限（2026-10 补充）：同一个待回答问题因换话题最多**重新追问 1 次**
（`ORGPILOT_MAX_TOPIC_REASKS`，默认 1），超过之后回复中不再附带追问（按新话题正常回复，
asks_clarification=false），但待回答状态保留。追问总上限：
`asked_rounds + reask_count` 达到 `max_clarification_rounds + max_topic_reasks`
（默认 3 + 1 = 4）时**停止追问**——来源是探针的，标记为「信息不全」并通知协调器
（处理方式同"多轮追问后仍不完整"）；来源是普通追问的，直接清除待回答状态。

示例：

- 待回答"支付SDK什么时候恢复？"时改问"周报这周还用写吗？"→ 回复 unsupported + 重新追问；
- 待回答时聊"今天的热搜"→ 回复 smalltalk + 重新追问；
- 第 2 次换话题 → 只按 smalltalk 回复，不再附带追问；
- 连续换话题直至总上限（第 4 次换话题）→ 探针来源标记「信息不全」并收敛。

## R10 时间约定

- 晚上/今晚 = 20:00；中午 = 12:00；早上/早 = 10:00；下班前 = 18:00；
  月底 = 当月最后一天 18:00；
- **只有日期没有时刻 = 当天 18:00**（如"明天"= 次日 18:00）；
- "下周X" = 下一个自然周（周一为一周起点）的周X；"周X""这周X""本周X"按本周内最近的该日理解。

## R11 expected_completion 只填完成时间

`expected_completion` 只填**任务完成或阻塞解除**的时间。**完成类事件**包括：
修好、修完、恢复、解决、完成、提测、上线、交付、合并——出现这些动词的时间就是完成时间：

- **已经发生**的完成（"已经修好了""已经上线"）**不填**——任务已完成，无"预计完成"可言；
- **将来**的完成（"今天能提测""明天修好"）**必须填**；
- 不填的还有：开始时间（"下周三开始压测"）、演示/评审时间（"5点半演示"）、
  定位原因的时间（"三点能定位"）、下次同步的时间（"明天再同步给你"）。

示例：

- "预计下午三点能定位" → 不填（定位原因 ≠ 完成）；
- "5点半给你们演示" → 不填（演示 ≠ 完成）；
- "压测第一轮可能要拖到下周三才能跑完" → 填（跑完 = 完成）；
- "预计明天下午5点能恢复" → 填（恢复 = 阻塞解除）；
- "商户后台今天能提测" → 填（提测 = 完成类事件，当天 18:00）；
- "收银台页面改版做完了" → 不填（已完成）。

## R12 顺带提及的任务

对消息里**顺带提到**的其他任务：

- 说它"可以开始了 / 随时能开始"是在说明**依赖已解除**，不是对该任务的状态汇报
  → 不为它输出条目；
- 明确说"不归我管 / 我没管"→ **不输出条目**（不知道就是不知道，不猜）。

示例：

- "支付SDK没问题了，压测那边随时可以开始" → 只输出 pay_sdk 的 claim，
  "随时可以开始"不产生 pay_e2e_test 的条目；
- "支付SDK可以收尾了，压测的准备我没管" → 只输出 pay_sdk 的 claim，
  不为 pay_e2e_test 输出任何条目。

## R13 out_of_scope 与 chitchat 的区分

- 向**机器人提出的、与项目协调无关的请求**（推荐餐厅、订会议室、查天气、写周报）
  → `out_of_scope`，回复 `unsupported`；
- **不含请求**的寒暄、吐槽、闲聊 → `chitchat`，回复 `smalltalk`。

示例：

- "附近有什么好吃的推荐吗？"（向机器人提请求）→ out_of_scope + unsupported；
- "今天地铁又挤爆了"（纯吐槽，无请求）→ chitchat + smalltalk。

## S. 系统确定性规则（代码完成，标注与系统行为对齐）

### S4 截止日判定由系统完成

claim 的 `expected_completion` **晚于**任务截止日 → health 取 **max(模型判断, delayed)**；
早于截止日时**不下调**模型的判断。标注与提示词都**不要**按截止日推断 delayed。

### S5 unknown 不产生 claim

`health_status` 为 unknown 或为空的 report_status / answer_pending 条目**不写 claim**；
在探针会话中**不算"已回答"**，按既有追问规则继续追问（受 3a.2 总上限约束，
到上限后标记「信息不全」）。

### S6 模糊的"看看进度"先回答，PM 附同步提示

意思模糊的"看看进度"（如"帮我看看现在的项目进度"）→ `query_status`，系统先用现有
状态回答（`query_answer`）；**发送者是 PM 时**，回复末尾附一句
"需要我向大家发起同步吗？"（只提示，不发卡片）；只有明确要求**向大家收集**时才是
`request_sync`（R8）。
