# OrgPilot 开发路线

> 2026-10-30 起执行。需求依据见 [`product/requirements-analysis.md`](product/requirements-analysis.md)（v0 假设稿）；缺陷依据见 [`full-lifecycle-scenario-design.md`](full-lifecycle-scenario-design.md) 第九节。

## 原则

- **验证环境**：开发和演示都在网页沙箱、回放场景和模拟团队里完成，用固定时钟驱动。真实飞书不在关键路径上，它只是一个适配器，等有条件时再验证。
- **先站得住，再加功能**：现有能力在完整项目周期里会出错（D1–D6），先修好，再扩展新能力。
- **同时开着的 PR 不超过 2 个**：合完一个再开下一个。
- **完成的定义**：每个功能或修复都要有回放场景或生命周期检查、测试、一项可度量的指标和一条文档；没有场景的功能不算做完。
- **每周例行**：
  - CI 是绿的；
  - 更新生命周期通过数和缺陷登记表；
  - 在沙箱里录一段 1–2 分钟的演示；
  - 更新 Notion 首页的"核心数字"和 08 页的路线图。

### 每个修复 PR 的完成标准

1. 从 `KNOWN_DEFECTS` 里删掉自己那一条。生命周期通过数要**恰好**增加该条登记的检查数，其他检查不能变化。
2. 针对根因加一个单元测试，不能只靠生命周期场景兜住。
3. `uv run orgpilot replay --all` 全部通过；`uv run pytest --cov=orgpilot` 通过，覆盖率不低于 90%；`uv run ruff check .` 通过；CI 是绿的。
4. 只对原本格式干净的文件运行 `ruff format`。
5. 开发日志加一条：修了什么，生命周期从多少到多少。
6. 一个缺陷一个 PR。两个 PR 并行时，`KNOWN_DEFECTS` 会在相邻行冲突，保留两边的删除即可。
