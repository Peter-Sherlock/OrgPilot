## 1. 目标与现有差距

目标链路：**收到消息 → 理解任务与意图 → 校验证据和权限 → 选择动作 → 执行 / 请求审批 → 解释结果**。
M2 先补这条链路的能力，不以调度器或真实飞书接入为前置条件。

| 输入 | 当前已核对的行为 | M2 目标 |
|---|---|---|
| 状态汇报、个人承诺、回答追问 | [Handlers](../src/orgpilot/intent/handlers.py) 已能记录 claim / commitment 并运行协调 | 保持已有行为与正式任务状态边界 |
| “我在等后端接口” | [IntentType](../src/orgpilot/intent/models.py) 已有 dependency_wait；[Guard](../src/orgpilot/intent/guards.py) 仍拦为 UNSUPPORTED | R1：建立等待事项、找上游确认、向 PM 说明影响 |
| “为什么改到周五？” | 当前查询主要返回任务现状，没有专门的原因处理入口 | R9：组合事件、Case、审批及执行证据 |
| “如果再延 3 天呢？” | 假设语气会被确定性护栏拦为 NOTED，避免变成事实 | R10：进入只读模拟查询；继续禁止假设写入事实 |
| 手动 `/同步` | 已有 PM 权限、确认卡片、成员探针及汇总 | 继续可用；定时发起 R4 后移 |

“先做消息驱动”不表示 M1 全部完成。D3 仍登记，不能把 58/59 写成 59/59。
这里的 R 编号是产品需求编号，与意图评测里同名的 R 编号不是同一组规则。

## 2. 前置能力：M2-0 项目上下文

任务标题不足以解释项目目标或交付标准；现有上下文也未包含完整依赖和业务资料。

## 3. 后续场景草稿：R1 依赖等待

以下场景不代表 R1 设计已经批准。PM 通知时机、等待解除确认和跨成员动作限额在 R1 实施前单独细化。

示例项目中，接口任务由后端 Bob 负责，前端 Alice 的页面任务依赖它。

| 步骤 | 收到的消息 / 证据 | Agent 应做什么 |
|---|---|---|
| 1 | Alice：“页面在等支付接口。” | 记录 Alice 对等待的陈述及来源；确定等待任务、上游任务和两端负责人 |
| 2 | 有两个接口任务，或现有依赖关系不足以定位 | 向 Alice 澄清，不猜任务、负责人或依赖边，不直接联系一圈人 |
| 3 | 上下游定位明确，责任人已登记 | 向 Bob 询问该接口的可交付时间；不是再次问 Alice “接口何时完成” |
| 4 | 初次等待事实已确认可定位 | 私聊告知 PM：“Alice 报告等待接口，Bob 的交付时间待确认”，附来源及已知依赖路径 |
| 5 | Bob：“明天 15 点可联调。” | 绑定到原等待事项；记录 Bob 自己的回复，向 Alice 和 PM 汇总可交付时间及影响 |
| 6 | 估计时间与正式排期冲突 | 提交可审查建议，复用 PM 审批门禁；不自动改期或改派 |
| 7 | 后续消息 / 正式源确认交付、取消等待，或双方否认 | 依据具体证据解除等待、关闭或转为冲突待核实；保留原始双方陈述 |

仅凭 Alice 说“在等接口”，不能把 Bob 的任务标成延期，也不能替 Bob 作承诺。
“可联调时间”与“任务完成时间”是不同槽位，不能直接塞入现有 expected_completion 而改变其语义。
Bob 给出时间后可以结束“等待回复”，但不能据此声称依赖已经交付；等待解除需要后续证据。

R1 第一轮边界：

- 只处理已有项目、成员和任务；依赖关系明确或经澄清确认后才跨成员联系。新增 / 修改正式依赖图另走显式授权。
- 采用独立的等待证据与 Case 类型，避免健康 reconcile 把健康度 unknown / on_track 的等待事项直接关闭；
  不借用伪造健康声明触发动作，不覆盖已结束健康事项或旧审批历史。
- 模型负责抽取任务引用和原话；确定性代码校验引用、收件人、当前事项、动作策略与证据来源。
- 追问、PM 私聊通知需要明确策略；不能借用群通知动作绕过审批。找不到上游负责人或 PM 时暴露缺口，不猜身份。
- 同一等待 episode 的重复消息只追加证据；同一上游负责人的未答问题合并，澄清沿用有限轮数，不能每条消息重问。
- 等待上下文必须能在重启后关联 Bob 的回复，也不能覆盖他原有的意图澄清或同步会话。
- 正常重投 / 重启须避免重复执行已确认动作；发送结果不明时停止自动重试并保留待核对记录。
  当前外发不具备跨平台 exactly-once 保证；R1 需验证自身动作记录，不依赖尚未实现的时间通知存储。
- 无人回复时保持可查询的等待状态，由新消息或 PM 手动操作继续；不增加后台超时、周期催问或到期升级。

## 4. 交付顺序

| 顺序 | 交付 | 重点边界 |
|---|---|---|
| M2-0 | GitHub 项目上下文接入、同步及有界主动查阅 | C1–C6 按 [分步计划](project-context-development-plan.md) 连续交付；只读，来源和业务状态分离 |
| M2-1 | R1 多轮依赖等待闭环 | 先固定等待 / 交付时间 / 解除等待的契约和场景，再实现路由、事项、策略与回复关联 |
| M2-2 | R9 “为什么”查询 | 返回可核实的变更链；提案、批准、实际执行分开；缺失记录不补编理由 |
| M2-3 | R10 “如果”查询 | 独立内存视图计算；标明假设，绝不提交事件、审批或成员通知 |

R9 的回答依据是日志和审批记录，而非让 LLM 推测动机；查询限定于当前有权访问的项目。
R10 首版只承诺基于已知 DAG 给出潜在受影响任务 / 路径及排期冲突；
当前 [DependencyAnalyzer](../src/orgpilot/dependencies/analyzer.py) 只是风险传播遍历，
没有工期、资源与工作日历模型，不能宣称能精确算出项目延期天数。

R6 请假、R7 会议待办、群聊旁听等不因“消息驱动”自动加入本轮范围。

## 5. R1 验收与回归要求

| 场景 | 验收要求 |
|---|---|
| 前端等待后端，后端回复交付时间 | 联系 Bob；等待事实与确认结果可区分，PM 收到影响说明；交付时间不是正式完成 |
| 模糊接口名、缺失负责人、多个候选依赖 | 先澄清 / 显示缺口，不误联其他成员 |
| 同一消息重复投递、不同消息重复描述同一等待 | 证据与动作去重；不产生多份活跃等待事项或重复问题 |
| 重启后收到 Bob 回复 | 恢复等待上下文，回复归属原事项；不丢失旧审批与执行历史 |
| Bob 否认等待 / 双方陈述冲突 | 展示各自来源并请求核实，不替一方判定事实 |
| 否定、提问、假设、未注册发送者、无依据任务引用 | 不伪造等待事实或触发错误跨成员动作 |
| 交付、取消等待、已完成任务与过时回复 | 正确关闭 / 忽略 / 待核实；不从旧消息恢复已经解除的事项 |
| 一条消息多事项、对方已有澄清 / 同步等待 | 正确关联并有限合并，不覆盖上下文或互相结案 |
| 正常发送失败、结果不明、重放历史日志 | 失败如实暴露，未知不自动重发；纯状态重放不触发外发 |

M2-0 在一个功能分支按 C1–C6 连续实施、逐阶段提交，最后一个 PR 统一审查；随后各消息能力独立交付，先完成 R1 再进入 R9。
验证包括对应多轮场景、关键单元 / 集成与重启失败测试、全量测试、覆盖率不低于 90%、Ruff 和回放。
冻结意图评测须回归；R1 从 UNSUPPORTED 变为可执行属于有意的契约变化，新增评测应单独版本化、
报告与旧基线的差异，不能只改 gold 或录制文件掩盖错误，也不能把旧录制通过等同于新抽取能力已验证。
本轮不使用真实 LLM 调用、真实飞书或计时后台来替代离线验收。

建议 R1 度量：上游定位准确数 / 总场景数、错误联系数、重复动作数，以及 PM 首次看到等待依据的消息轮次。
保留生命周期 58 个已有通过项和唯一 D3 登记；本功能不以修复 D3 为验收条件，也不得删除该登记。
