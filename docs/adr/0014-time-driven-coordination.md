## 2. 建议采用的语义

### 2.1 时间与组织事实

1. 一轮业务评估对一个项目只读取一次 `Clock.now()`，该 `now` 用于判断义务、记录观察和生成计划。
   外发作为独立执行步骤，以同一个注入时钟读取 `attempt_at`，重新核对状态、时段和预算；
   不能沿用排队前的旧 now 发送，也不能修改已经持久化的首次观察时间。
   全部比较使用带时区的瞬时；展示和工作时段使用项目现有业务时区，默认 `Asia/Shanghai`。

   > **代码核对 K5：**当前只有进程级业务时区，没有按项目配置的时区。详见文首核对表。

2. 任务逾期条件严格为 `now > deadline`；恰好相等不逾期。`deadline=None` 不扫描。
   承诺同样使用严格 `now > due_at`；没有 `due_at` 的承诺不做时间提醒。
3. 扫描不写 `task.health_reported`，不修改 `workflow_status`、`health_status`、负责人或正式截止时间。
   “未记录完成”必须如此表述，不能替成员断言“你没有完成”。
4. **推荐：时间流逝只记录 `overdue_unconfirmed` 观察并启动跟进，不直接把承诺状态写成 `BROKEN`。**
   临近到期也不写 `AT_RISK`。承诺仍可为 `ACTIVE`，同时具有“逾期未见兑现”的跟进事项。
5. `FULFILLED` / `BROKEN` 继续由真实匹配事件的业务时间决定，保留 D4 的严格边界。
   晚到的按时兑现证据可以让跟进停止，不必先把一个由“没收到消息”推断出的违约状态改回来。
   这不等于已经实现通用乱序事件处理；摄入被拒绝时必须暴露错误，不能用摄入失败证明成员违约。

因此 R3 的“违约升级”在无兑现证据时具体表述为“承诺已过期，截至本次检查尚未记录兑现，请 PM 确认”；
存在实际迟到匹配事件时，才使用 `BROKEN` 所表达的“事已完成，但时间承诺未守住”。

### 2.2 建议默认参数（全部为提案）

| 参数 | 默认值 | 解释 |
|---|---|---|
| 时间协调总开关 | 关闭 | 未来显式配置 `ORGPILOT_TIME_COORDINATION_ENABLED=true` 才启用消息轮次评估和后台任务 |
| 时间通知真实外发 | 关闭 | 未来独立配置 `ORGPILOT_TIME_EXTERNAL_SEND_ENABLED=true`；不借用旧分支的写闸 |
| 扫描间隔 | 60 秒 | 仅决定检查频率，不把每个间隔变成一个业务事件 |
| 承诺到期前提醒窗口 | 4 小时 | 按实际经过时间计算，`0 < due_at - now <= 4h`，每条承诺最多一次；任务不另发到期前提醒 |
| 可主动联系时段 | 周一至周五 09:00–18:00 | 按项目业务时区；18:00 已属安静时段；暂不支持法定节假日历 |
| 成员主动通知冷却 | 2 小时 | 同项目、同接收者，跨任务合并计算 |
| 成员主动通知上限 | 滚动 24 小时最多 3 条 | PM 作为普通接收者时也受此约束；以平台调用额度占用时间计数 |
| PM 升级通知上限 | 滚动 24 小时最多 2 条 | 同时受上述冷却和总上限约束；多个 PM 取按 ID 排序的首位 `pm` |
| 首次追问后等待 | 2 个工作时段小时 | 从确认发送开始算；安静时段不消耗等待时间 |
| 单条合并消息 | 最多 5 个事项 | 同一任务的截止时间与承诺合成一项；其余继续排队，不静默丢弃 |
| 自动发送尝试 | 每条通知最多一次 | 结果不明不重试；明确失败也不由下一次扫描自动重试 |

这些是减少打扰的初始默认值，不是已经测得的最优参数或生产 SLO。修改时必须保留验收场景。

## 3. 谁推进时间、何时运行

### 3.1 一个业务入口，三种调用来源

拟由网关提供 `run_time_cycle(project_id, now, reason)` 入口，调用同一个确定性的时间评估器：

| 来源 | 如何推进 | 约束 |
|---|---|---|
| 场景 / 测试 | `FrozenClock.set/advance` 后显式运行一轮 | 不启动线程、不真实 sleep、不访问外网 |
| 网关后台 | FastAPI lifespan 内单个可取消任务，启动时检查一次，之后每 60 秒检查 | `SystemClock` 只提供当前时间；关闭时等待在途轮次退出后再关闭数据库 |
| 消息 / 审批 / 手动协调 | 处理新事件后、同一项目轮次内复用时间评估 | 不能与后台形成两条不同的判断或去重规则 |

> **代码核对 K1、K4：**lifespan 已有资料后台任务；`/项目` 消息不运行协调轮次，不能触发时间评估。详见文首核对表。

时间评估与通知模板不调用 LLM；成员实际回复后，才走既有消息路由及其调用预算。
后台项目清单来自持久化事件库，而非“本进程收过消息的项目”缓存。重启没有新消息时也能发现项目。
独立 `start-feishu-ws` 与 FastAPI 同时运行不得各自启动调度器；M1 只允许一个指定的网关写者。

> **代码核对 K2：**当前代码没有跨进程单写者保护。详见文首核对表。

按项目串行处理消息、审批、任务更新和时间轮次；现有对话快照锁不等于这个项目锁。
锁内重新读取权威状态、判断和持久化，避免旧扫描覆盖刚发生的完成或批准改期。
实现时使用统一加锁入口和不再二次加锁的内部方法，规定项目锁在对话状态锁之前，防止重入死锁。
外发步骤持有项目锁直到发送结果登记，以有界网络超时防止长期阻塞；网络等待期间不持有数据库事务。
这只能保证按已接收状态串行决策，不能撤回已经发出的消息或预知尚未摄入的完成事件。
慢速 LLM 提取可在锁外进行，但其结果在锁内应用前仍须校验当前状态。

> **代码核对 K3：**协调路径目前没有项目锁，现有的仓库级锁只保护资料同步。详见文首核对表。

### 3.2 停机、回拨与发送开关

- 启动补查只判断“现在仍有效的义务”。不补发停机期间每个扫描点，也不补发已经过期的到期前提醒。
- 某项目单轮失败记为失败，其他项目继续；该项目下一轮从持久化记录恢复，不把失败记成成功。
- 持久化最后评估时间。时钟回拨时暂停新增时间观察和主动外发，保留既有记录并报告时钟异常；
  等时间追平或人工处理，不能通过回拨重置预算、撤销历史发送或重新获得提醒次数。
- 总开关关闭时不创建后台任务，消息轮次也不新增时间动作；测试 / 场景须显式启用。
  独立纯预览只返回计划，不写事件、Case、额度或发送记录。
- 启用扫描但关闭真实外发时，可以保存观察与待通知事项，真实适配器不得调用；Mock 场景可以正常模拟发送。
  关闸不等于送达，不启动成员回复计时；重新打开后必须重新校验待发事项。

## 4. 义务身份与判断规则

### 4.1 截止时间版本必须有来源

义务主键为 `(project_id, kind, subject_id, due_revision, responsibility_revision)`。

- 任务的 `due_revision` 来自最后一次设置 deadline 的正式事件 ID 及规范化后的 UTC 截止时间。
  任务负责人修订来自最后一次设置 owner 的正式事件；标题修改、普通汇报不产生新截止时间版本。
  现有 TaskState 没有这些按字段的来源标识，后续实现需从日志确定并投影保存，不能拿
  `last_update_at` 或 `source_event_ids[-1]` 代替。
- 承诺以不可复用的 `commitment_id`、创建事件及原 `due_at` 为身份。变更承诺使用既有 supersede +
  新承诺机制；任务改期不自动延长个人承诺，改派任务也不自动替换承诺人。
- 截止时间 A → B → A 是两个不同的正式修订，不复用旧 A 的提醒资格；仍受接收者共享预算约束。
- 改期、完成、承诺 supersede、正式改派发生时，取消旧版本未发通知并关闭或交接旧时间事项。
  新负责人可以获得新事项，旧负责人不再收到该任务的排队追问；已发送记录保留。

### 4.2 任务截止时间跟进（M1-8 / M1-9）

| 条件 | 决定 |
|---|---|
| 未到截止时间，或任务已 `done` | 不产生任务时间事项；取消旧版本未发动作 |
| 已逾期，存在正在处理同一任务的健康追问或改期审批 | 记录逾期依据，关联已有 Case，不再发第二个相同问题或审批卡 |
| 已逾期，当前有效的主风险声明给出了未来 ETA | 正式截止时间仍显示逾期；不重复问同一个 ETA，最早在该 ETA 也过期后重新评估 |
| 已逾期、未完成、没有未来 ETA，也没有正在处理的等价事项 | 创建独立 `task_overdue` 时间 Case，按预算向任务负责人追问一次 |
| 负责人回复了新的未来 ETA | 停止无回应计时；需要改期时优先复用已有健康事项审批，无可接管事项时由时间 Case 提案给 PM，不能双重提案 |
| 负责人仅口头说完成，正式任务仍未完成 | 保留来源，停止把对方当作“未回应”；请求在正式任务源确认，不自动设 `done` |
| 平台确认接受追问后，已满 2 个工作时段小时仍无有效回复 | 申请一次 PM 私聊升级；不反复追问成员 |

主风险声明沿用现有“严重度最高、同级取最新、再按 ID”的确定规则，不在此重做冲突合并。
无明确 ETA 的一般闲聊不构成无限延期依据。收到有效 ETA 后，不因每个 tick 再次联系成员；
同一截止版本已经用过的追问次数仍保留，后续异常只进入尚未使用的 PM 升级阶段。
只有回复确实构成新风险证据时才走 D1b；不能为了拿到改期审批而伪造风险声明。
时间 Case 复用 `PROPOSE_RESCHEDULE` 与现有 PM 审批门禁，仍需绑定自己的当前审批 ID；
接管/审批建立成功前不把整个事项标为已解决。

`case:task-health:<task>` 的历史结果保持原样。新增 Case 拟增加 `kind`，旧快照默认 `task_health`；
健康事项继续按原规则 reconcile，时间事项由独立规则处理，不能被“健康度 unknown/on_track”直接结案。
时间 Case 使用 `case:time:<义务主键的摘要>`，完整主键另存并校验，满足现有 SQL ID 长度限制。

### 4.3 承诺跟进（M1-10）

范围沿用当前事件契约：`target_type=task`，谓词为 `workflow_status` 或 `health_status`，
只依据匹配事件结算；不因当前状态看起来相似就补造兑现事件。

| 条件 | 决定 |
|---|---|
| ACTIVE、有 due_at、进入 4 小时提醒窗口 | 给 `commitment.actor_id` 一次私聊提醒；保持 ACTIVE，不创建风险事项 |
| now 恰好等于 due_at | 不判逾期，也不再补发“即将到期”提醒 |
| now > due_at，尚无兑现证据 | 记录 `overdue_unconfirmed`，创建 `commitment_due` 事项，申请一次 PM 私聊升级 |
| 已有同任务的截止时间追问 / PM 升级 | 合并消息，保留任务和承诺各自的证据、阶段及去重键 |
| 已 FULFILLED 或 SUPERSEDED | 不提醒；撤销未发动作 |
| 任务已 done，但承诺仍 ACTIVE、没有匹配的兑现事件 | 停止成员追问并进入可见的人工核对项；不自动改为 FULFILLED / BROKEN |
| 实际迟到兑现，被 D4 结算为 BROKEN | 不再向已完成事项的承诺人追问；保留违约历史，未通知过 PM 时仍可合并一次事实通知 |
| 晚到但业务时间在 due_at 以内的匹配事件 | 按 D4 兑现；取消未发的逾期通知，关闭误差已澄清的等待，保留原观察及补充证据 |

承诺人和任务负责人不同就分别按各自责任联系，不能向报告风险的旁观者索要恢复承诺。
找不到登记的责任人或 `pm` 时，记录“需要人工处理”，不回退为群发或任意指定审批人。

> **代码核对 K6：**现有改期规划在没有 PM 时回退给任务负责人，与本条规则相反。详见文首核对表。

## 5. 去重、事件与执行结果

### 5.1 记录观察，不制造每分钟事件

拟新增 `time.obligation_observed`，仅在首次进入 `due_soon` / `overdue_unconfirmed` 等阶段时记录。
建议字段：义务完整主键、阶段、原 due_at、`effective_at`、首次 `observed_at`、正式来源事件引用。
新增内部 `EventSource.TIMER`，`actor_id=None`；仅内部时间入口或显式场景入口可产生，
消息提取与公共事件摄入不能通过自报 source 授权一个计时观察。

事件是“系统在 observed_at 基于已收录证据观察到什么”，不是成员汇报。
不把 `occurred_at` 回填成假装当时执行过的截止时刻；`effective_at` 才表示原到期时刻。
事件 ID 基于逻辑身份；首次写入的 observed_at 和完整载荷必须持久化，后续复用原记录。
不能每次用新 now 重造同一 ID，否则会触发现有事件内容冲突检测。

组织状态投影只保留可追溯的时间观察，不据此改官方任务状态或强制兑现/违约。
新增投影字段或规则时必须更新投影缓存版本，旧缓存由事件重放重建，沿用 D6 的升级约束。

### 5.2 每个逻辑动作只有一个发送身份

`notice_key = (义务主键, 阶段, 接收者, 通道)`，不包含 tick 序号、进程启动时间或 `_turn_count`。
通知阶段明确分为 `due_soon_reminder`、`overdue_owner_check`、`overdue_pm_escalation`；
同一义务同一阶段最多自动尝试一次。PM 换人不刷新已发送/failed/held 阶段的次数；
仅未尝试的通知可以撤销后改投当前 PM，实际迟到证据也不另开第二个 PM 通知阶段。
合并消息的批次 ID 由排序后的 notice_key 集合确定；已生成批次冻结内容，变化则撤销未发批次后重新评估。
数据库对完整 notice_key 做唯一约束；摘要 ID 还需校验完整输入，不能仅凭短哈希误认同一义务。

拟新增窄范围 `SqlTemporalNoticeStore`，保存待发内容、原因引用、状态、额度占用和发送结果。
**当前主线没有通用 outbox**，不得把旧分支草稿当作已可复用实现，也不在本阶段迁移全业务外发。

```text
prepared → sending → sent
                   → failed
                   → held（超时、异常或崩溃后结果不明）
prepared → cancelled（已完成、已改期、已换负责人或证据过时）
```

- 时间观察事件、Case 变更、notice 意图在一个短数据库事务中提交；存储接口须支持同一个 session。
  不把跨表多个 commit 称为原子提交。外部网络调用不在数据库事务内执行。
- 发送前再次检查当前版本、完成/兑现状态、收件人、安静时段和预算；用条件更新原子占用 `sending`
  与预算，再调用适配器。Prepared 无额度、无发送行为；Sending 已占用一次尝试。
- 只有适配器确认平台接受才记 `sent`；平台接受不证明用户可见。确认后才登记等待回复的起点。
  发送意图保存待回答上下文，结果不明时不以“无回应”继续升级；可信的实际回复可用于对账与收敛。
- 对同一义务，在发送前和发送成功落盘时绑定同一批次及阶段，避免合并变化后再次发送已尝试子项；
  实现必须同时校验阶段唯一性与 notice_key 唯一性，不能只用更换接收者后的新键绕过去重。
- 明确失败记 `failed`，超时或进程在 sending 阶段退出记 `held`。两者都占用本次预算，均不自动重试。
  重启可以继续 prepared；不能恢复发送 sending/held，须人工核对后另行批准处理。
- 这是一项“自动最多一次尝试”的取舍：优先避免重复打扰，可能漏发；必须让待处理/失败/未知结果可见。
  不宣称跨平台 exactly-once。现有业务路径的至少一次边界不因此自动消失。

> **代码核对 K7：**现有事件和状态存储各自开启 session，还不支持单事务提交。详见文首核对表。

### 5.3 Case、审批和终止原因

- 新增低风险私聊动作拟为 `REMIND_COMMITMENT`、`NOTIFY_PM`，都必须经过独立策略检查和发送预算。
  不能伪装为已有 `NOTIFY_GROUP` 以绕过其审批，也不能直接调用真实平台跳过记账。
- Task-overdue Case 在 prepared / held 阶段保持 OPEN；确认追问发送后才 WAITING_FOR_RESPONSE。
  PM 升级确认发送后才记 ESCALATED，失败仍保留待处理状态。承诺逾期单独升级不需要先重复问成员。
- 同一项目同一任务的任务逾期与承诺逾期，可以合并一次负责人消息、一次 PM 消息；二者的独立原因和历史不能覆盖。
- 待答上下文绑定通知批次、任务和义务 ID，持久化到现有对话存储；已有意图追问或同步等待时先合并或延后，
  不能覆盖它。只有能关联该义务的有效回复才停止无回应计时；闲聊不算，任务指向不明时先澄清。
  回复中的 ETA / 完成声明走既有提取与正式状态边界，不能由计时器直接伪造事件。
- 只有被延后或未确认发送的时间事项时，拟新增 `waiting_delivery` 终止原因，避免输出 all_resolved。
  既有 WAITING_RESPONSE / WAITING_APPROVAL 优先级不变，历史升级仍不能污染后续轮次（D5）。
- 改期等高影响动作继续通过 PM 审批；时间任务不得自动调用 UPDATE_TASK、消费旧审批或增加审批权限。

## 6. 打扰预算与安静时段

1. 定时主动消息、时间触发的追问和升级共享接收者预算，不能换任务、换 Case 或重启绕过。
   成员主动发消息后的直接回答不算定时主动打扰；必要追问仍受既有对话轮数上限约束。
   PM 明确请求的同步保留其显式授权，但其主动探针也计入后续自动联系预算，不能由代码伪造“手动”来源。
2. 同一接收者的一轮候选先合并，再检查冷却和滚动 24h 预算；失败/未知发送占用预算。
   预算按持久化的实际尝试时刻计算，跨本地午夜不清零，重启不清零；不逐条先占额度再合并。
3. 优先级为逾期后的跟进/升级在前、临近承诺提醒在后，同级按最早到期、完整主键排序，保证回放一致。
   未发送项继续排队；下一轮先重新校验，不补发已失效的“即将到期”。
4. 安静时段只限制联系，不改变 deadline、due_at 或是否逾期。周五 17:30 确认发出的追问，
   等待 2 个工作时段小时后应在周一 10:30 到期，不能在周末把成员当作超时未回应。
5. 夜间到期且恢复时已逾期的承诺跳过到期前提醒，只考虑逾期阶段；关闭的义务不追溯补发历史通知。
   预算和安静时段不阻止已登录 PM 在控制台查看积压，也不阻止成员主动回复。
6. 工作时段计算基于 IANA 时区与实际瞬时；夏令时切换不能产生两次额度或重复相同通知。
   法定节假日、成员个人时区、跨项目全局预算留待真实团队需求验证，本版明确只保证单项目预算。

## 9. 备选方案与取舍

- 只靠下一条消息触发：无法解决沉默逾期，否决。
- 固定 cron 只在工作日上午执行：机制简单，但不能表达具体 due_at 和一致回放；采用扫描 + 业务时段门禁。
- 到点直接 BROKEN、到期前直接 AT_RISK：混淆时间观察与事实证据，引入晚到消息补偿和误判，本提案不采用。
- 每个 tick 一次全员提醒：缺乏义务身份和预算，重启后易重复，不采用。
- Redis/Celery/分布式 leader：当前单实例 SQLite 范围用一个受控后台任务足够，规模化另行设计。
- 自动重试全部失败或未知发送：可能重复打扰。本版只恢复未尝试的 prepared，失败和未知结果保留人工核对入口。
