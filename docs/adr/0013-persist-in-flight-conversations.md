# ADR-0013：进行中的对话状态与同步会话持久化

- 状态：**Accepted**（2026-10-20 实现于 `feat/conversation-persistence`）
- 日期：2026-10-20
- 编号说明：`origin/wip/m3-approval-acceptance` 上有 0010–0012 的草稿，为避免冲突跳到 0013

## 背景

ADR-0004 之后，事件、OrgState、Case 和审批都能在重启后恢复，但意图层和同步协调器还有两块状态只在进程内存里：

1. `DialogueStateStore`（`intent/dialogue.py`）：待回答的追问 `PendingClarification`（问题、目标任务、已合并的半成品 claim、缺失槽位、追问轮数、换话题重问次数、来源 probe / clarify）和待确认的同步卡片 `PendingSyncConfirmation`；
2. `ProgressSyncCoordinator._sessions`（`coordination/sync_coordinator.py`）：进行中的 `/同步` 会话，包括向谁发了探针、谁已回复、回复是否完整、最后活动时间（超时依据）和简报。

重启 uvicorn 后两者全丢：成员对追问的回答被当成一条新消息处理（不带任务的回答会被反问“是哪个任务”），PM 点同步卡片得到“已失效”，进行中的同步永远等不到简报。2026-10-20 的开发日志把它推迟，理由是两块必须一起做：只持久化对话状态，探针追问会指向已经不存在的会话。

## 决策

### 1. 范围

持久化上面两块状态的全部字段。路由行为不变：同一条消息在重启前后得到同样的分类上下文、同样的处理结果和同样的回复。

### 2. 存储形式：沿用快照表，不写事件

| 表 | 粒度 | 对照 |
|---|---|---|
| `dialogue_snapshots` | 每个项目一行 JSON（`DialogueSnapshot`：按发送者存追问和确认卡片） | 与 `state_snapshots` 相同 |
| `sync_sessions` | 每个会话一行 JSON，附 `status` 列；自增 `id` 记录发起顺序 | 与 `coordination_cases`、`approval_requests` 相同 |

- 会话按 `id` 顺序加载。`get_active_session` 依赖发起顺序，而 `FrozenClock` 下两个会话的 `created_at` 可以相同，不能靠时间排序；
- 新表由 `init_db` 的 `create_all` 建出，已有的 `orgpilot.db` 下次启动时自动补表，不需要迁移。

### 3. 何时写：每轮结束时整体保存

- 两个存储的接口保持同步、保持内存副本。路由在 `handle_message`、`handle_sync_card_action`、`start_sync` 结束时调用 `GatewayService.save_conversation_state`，把该项目的对话状态和同步会话放在**同一个事务**里写入，重启后不会出现“探针追问已清除、会话还在等这个人”的组合；
- 保存发生在 `processed_messages` 记录之前。`processed_messages` 是一轮的最后一次写，和事件先于它写入的现有顺序一致：两者之间崩溃时，平台重投的消息会被重新处理，而不是被当作已处理丢掉；
- 路由中途抛错（例如回放录音缺失这类基础设施错误）也会保存：数据库反映的是进程接下来继续使用的内存状态；
- 导出和写入在同一把 `asyncio.Lock` 里完成，两轮交错时最后落库的一定是较新的快照；
- 序列化结果和本存储上次写入或读出的相同时跳过写入，没有变化的轮次不产生写操作。这依赖单写者假设，与 README 的单实例部署一致；
- REST `POST /sync` 不经过路由，启动会话后单独保存一次。

### 4. 何时读：首次访问时加载

- 同步会话：`get_sync_coordinator` 第一次为某个项目构建协调器时加载；
- 对话状态：路由第一次处理某个项目的消息、卡片回调或 `start_sync` 时加载一次。加载前已经在内存里登记的条目更新，保留内存里的那一份（测试和评测通过 `register_*` 构造状态时依赖这一点）；
- 读不出来的快照（例如以后删了模型字段，`StrictModel` 禁止多余字段）记一条 warning 后按不存在处理，下一次保存覆盖它。这只会退化成本 ADR 之前的行为，不会让该项目之后的每条消息都报错。

### 5. 时间

- 加载时不判断过期，也不改写任何时间戳。追问 24 小时、确认卡片 30 分钟、会话空闲 24 小时，仍然在访问时由持久化的 `created_at` / `updated_at` 与 `service.clock` 计算，所以重启前后的结论一致；
- 持久化的时间必须带时区，遇到不带时区的时间直接 `ValueError`，规则与事件时间相同。pydantic 的 ISO 8601 往返保留同一瞬时和同一 UTC 偏移；`ZoneInfo("Asia/Shanghai")` 读回后是固定的 `+08:00`，所有判断只比较瞬时，不受影响；
- 行上的 `updated_at` 元数据与其他存储一样用墙钟（`architecture.md` 第 3 节的约定），它不参与任何判断。

## 备选方案

- **事件溯源**（把追问、确认、探针写成事件，重放得到状态）：最符合内核的风格，但这些是对话层的临时状态，不是组织事实；需要新增一批事件类型和投影，回放场景和评测都要跟着改，范围远超“重启不丢”。事件日志又不可删除，24 小时就过期的对话数据会永久留存；
- **每次调用即写（write-through）**：处理器和协调器大量原地修改条目（`pending.reask_count += 1`、`entry.claims = ...`、`probe.status = ...`），评测工具也直接改 `coordinator._sessions`。全部改成显式的更新接口改动面大，漏一处就是一个只有重启后才出现的缺陷；
- **只持久化对话状态**：2026-10-20 已否决，见背景；
- **存储改成异步、去掉内存副本**：每次读取都查库，所有调用方都要改成 `await`，包括同步的协调器和评测工具；
- **在 lifespan 关闭时统一保存**：只覆盖正常退出，进程崩溃或被杀时照样全丢；
- **单独的 KV 存储（如 Redis）**：多一个依赖，和“一个 SQLite 文件就能演示”的定位冲突。

## 后果

正面：

- 重启网关后，成员对追问的回答、PM 点确认卡片或回复“好的”、进行中的同步收敛并生成简报，都和不重启时一致；过期和超时仍按原始时间计算；
- 演示手册不再需要“演示中不能重启”的提醒。

负面 / 边界：

- **至少一次**：副作用先于保存发生。例如会话超时时简报已经发给 PM、快照还没写入就崩溃，重启后会再超时一次、再发一次简报；探针已发出、会话还没保存时崩溃，会话丢失，需要 PM 重新 `/同步`，成员会收到两次探针；
- **仍只在内存里的状态**：`LLMIntentClient.spent_usd`（`--max-spend-usd` 预算按进程计，重启清零）和 `metrics`；飞书 `tenant_access_token` 缓存（重启后重新获取，无影响）；适配器的 `audit_log`；`CoordinationAgent._turn_count`（每次请求都从事件库重放出新的 Agent，本来就从 0 开始，与重启无关）。意图层没有 LLM 响应缓存，回放录音在磁盘上；
- **单写者**：多个实例同时写同一个库会互相覆盖对话快照（与 ADR-0004 的单实例限制相同）；
- **没有清理**：已完成的会话一直留在 `sync_sessions` 表里，与之前一直留在内存里相同；
- 每个项目首次访问多一次读取，每轮最多多一次写入。

## 测试

`tests/test_conversation_restart.py`，文件型 SQLite（`tmp_path`）+ `FrozenClock`。每个流程跑两遍：一遍不重启，一遍在标记处用同一个库重建网关（新的引擎、服务、路由、适配器和钉在同一时刻的时钟），两遍的结果必须完全相同：

- 路由发出的追问 → 重启 → 不带任务名的回答经恢复的追问落到正确任务；
- 确认卡片 → 重启 → 点按钮 / 回复“好的”都能发起同步；同一场景经 `build_gateway_service` 和飞书 webhook 再跑一遍；
- `/同步` 一人已回复 → 重启 → 另一人回复后会话收敛、简报发给 PM；再重启一次，完成状态和已清除的追问仍在；
- 过期：追问 25 小时后、卡片 31 分钟后、会话空闲 24 小时 1 分后仍然过期或超时，而且重启距离都不到 TTL，所以“恢复时把时间戳重置成重启时刻”的实现会让这些测试失败；
- 存储细节：时间往返精确到微秒且偏移不变；不带时区的时间被拒绝且不写入；会话按发起顺序加载；内存里已有的条目优先；读不出来的快照被丢弃、不阻断消息处理。

另外用两个故意改坏的版本核对过测试的区分度：完全不恢复时 10 个测试失败；恢复时把时间戳重置为当前时刻时，4 个过期 / 超时测试失败。
