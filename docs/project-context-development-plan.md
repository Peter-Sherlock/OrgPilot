## 1. 首版退出时应具备的能力

单个项目接入一个 GitHub 仓库，在指定范围内同步 Markdown、Issue、PR、普通评论及 PR review。
通过 `/项目 <问题>` 回答目标、术语、职责、交付条件和已接入的工作记录；每项事实能定位到资料修订，
不清楚或不可读的内容有明确缺口提示。同期更新、通知遗漏、重启和撤权后不继续使用失效的当前摘要。
同一问题可在允许范围内搜索、阅读原文、沿关联补读和查看正式任务状态，直至有依据回答、澄清或按明确原因停止；
查阅不增加新资料来源，也不启动业务协调。
四类工具、统一预算、停止结果与循环验收以 [ADR-0015 第 7 节](adr/0015-github-project-context-sync.md) 为准。

首版不写 GitHub，不接管现有任务主记录，不改 OrgEvent / Case / 审批，不联系其他成员。
普通消息和冻结意图提示词不自动改用新资料；后续 R1 单独开启对应上下文版本。
CI、部署与业务验收证据尚未接入，因此不能凭 PR 合并回答“已经可用 / 已上线”。

## 3. 分步交付

下面 C1–C6 对应 M2-0.1–M2-0.6。后续整包开发在一个功能分支按依赖顺序连续推进，每阶段验证通过后独立提交，
自动进入下一阶段，不因完成某一步而重复请求确认；最终准备一个可审查 PR，不自动合并。
本次不创建分支、提交或 PR。文件落点均为计划，尚未创建；测试以实际行为为验收对象。

| 步骤 | 交付内容 | 前置依赖 | 本步完成条件 |
|---|---|---|---|
| C1 / M2-0.1 | 资料契约、独立持久化与版本身份 | ADR-0015 审查完成 | 离线来源记录可保存、恢复、去重；不接 GitHub |
| C2 / M2-0.2 | 只读连接器与首次范围导入 | C1 | 能准确读取并报告覆盖，尚不声称已经形成可用问答 |
| C3 / M2-0.3 | 持久化通知、增量刷新、补查与恢复 | C2 | 原始资料可持续收敛；不调用协调轮次或发送成员通知 |
| C4 / M2-0.4 | 事实、关联、资料代次、ContextBuilder 与四类只读工具 | C3 | 版本固定、授权与读取边界可验证；尚未接入聊天问答 |
| C5 / M2-0.5 | `/项目` 入口、有界主动查阅循环与问答 | C4 | 循环预算、停止及引用可验证；不启用 R1 或普通意图提示词注入 |
| C6 / M2-0.6 | 集成验收、观测与可选真实只读验证 | C5 | 报告离线与真实证据的各自结果，完成后停止 |

### C1：来源契约与存储

拟议落点：`knowledge/models.py`、`storage/project_source_store.py`、`storage/models.py`。

- 冻结绑定、来源对象、修订、同步日志、覆盖、代次及 ProjectReadSession 的具体表映射、状态和值域。
- 定义仓库 / 对象稳定身份、评论子对象身份、change_sequence、内容哈希、共享版本和来源命名空间。
- 支持调用方共享 session，避免每个 store 各自 commit 后声称跨表原子性；默认仅新增表。
- 记录 metadata、原文、段落引用、不可用原因；凭据引用与资料内容分离。
- 增加查阅会话和预算预留 / 结算账本；同消息幂等，未知模型消耗不记零，中断后不恢复成新预算。

验证：重复读取不生新版本；A→B→A 保留三次修订；同投递 ID 不同载荷拒绝；跨项目隔离；
提交中途失败完整回滚；关机重开后记录保持；预算预留 / 结算和消息冲突保持一致。使用注入 Clock，不依赖真实日期。

### C2：只读连接器与首次导入

拟议落点：`github/client.py`、`knowledge/importer.py`，Mock 客户端与固定响应 fixture。

- 文档固定 commit 读取；工作记录采用稳定平台 ID。区分 Issue 与 PR，正确处理重命名、open / closed 和普通评论。
- 完整处理分页、条件读取、超限、权限错误及有界重试；记录每类资料的覆盖状态。
- 将 App 端点与权限逐项列出验证；业务接口仅提供读取，认证换 token 单独识别。
- 导入输出可审查的范围、版本、缺失和冲突清单；不写 OrgEvent，不运行 Agent。

验证：多页内容完整；相同标题 / 不同对象不误合并；过滤前后范围正确；部分失败不得标完整；
403 / 404 不误判删除；超过上限可见；无外部网络也能用 Mock 客户端完成测试。

### C3：通知、增量与补查

拟议落点：`github/sync.py`、`gateway/routes/github.py`、`gateway/app.py`、配置模型及独立同步存储。

- 验签后持久化 inbox 并快速响应；单项目 worker 刷新当前对象，按投递身份去重并保留失败。
- 初始导入期间先保存通知 / 补查起点，扫描后核对；通知乱序不能回滚当前对象。
- 来源修订、检查点与 inbox 完成状态共享事务；刷新任务中断后可恢复。
- 手动补查、启动恢复及默认关闭的定期补查；定期补查仅刷新资料。
- 删除、退出范围和失去权限使当前来源不可用；完整枚举前不得按缺少一页推断对象不存在。
- 网关关闭先停止接收 / worker 并保存处理状态，再关闭数据库；独立飞书监听器不另启第二个同步写者。

验证：重复 100 次、乱序、丢通知、父对象时间不变而子评论编辑；读取 / 提交各断点重启；
限流退避与失败上限；关闭开关后不后台访问 GitHub；纯资料刷新前后 events、Case、审批不变。

### C4：资料代次、上下文与只读查阅工具

拟议落点：`knowledge/derive.py`、`knowledge/retrieval.py`、`knowledge/context.py`、`knowledge/read_tools.py`。

- 对来源快照做段落切分、事实提取与显式关系解析；模型候选关系不成为正式依赖。
- 建立项目概况、术语、交付约定和版本化摘要；记录每条断言的确切证据和提取版本。
- 分离 observed 新来源与 published 代次；原始内容变化后旧依赖摘要立即标为过时。
- staging 全部校验后再切换指针；失败不发布半成品，绑定或授权变化时作废构建结果。
- ContextBuilder 组合资料与只读 OrgState；精确 ID、确认别名及文本检索优先，带证据清单、缺口和大小上限。
- 共享授权在召回前过滤，所有派生内容继承其来源的可用性；不泄露未授权来源的标题或结论。
- 实现 ADR-0015 第 7.4 节四类工具：search_project、read_source、get_related_items、read_task_state。
  服务端注入会话身份与版本；cursor、来源 ID、参数和返回量严格校验，不接受裸 URL、Shell、SQL 或写操作。
- 初始检索与补读共享预算接口；提供可定位的证据片段、截断 / 失败标记和工具结果缓存。
  重复参数可命中缓存，但仍计调用；新证据按修订和位置识别，不能将同一片段反复算作进展。
- 固定资料代次与正式状态读视图；每次读取前后检查授权和有效性，不让模型直接触发 GitHub 同步。

验证：项目目标 / 交付条件有对应原文；文档升级后检索与摘要更新；无关提交不重复提取；
歧义、冲突、未读取历史、预算截断均可见；构建时撤权 / 改范围 / 源再次更新，不能发布错误代次；
四类工具的非法参数、跨范围、分页、重复缓存和会话版本隔离均通过，不写任何正式业务记录。

### C5：多轮主动查阅、项目问答与消息入口

拟议落点：`knowledge/service.py`、`knowledge/read_loop.py`、`knowledge/answerer.py`、`intent/router.py`、回复模型与帮助文本。

- 增加 `/项目 <问题>`，顺序为消息幂等 / 成员检查 → 项目命令 → 原探针与意图路径。
  不把项目问题当作 probe 回复，不清空、续期或覆盖原待答 claim / 同步会话。
- 由独立 ProjectReadOrchestrator 调用 ContextBuilder、只读工具和问答生成器，执行 lookup / finish / ask_clarification / report_gap。
  它不调用 CoordinationAgent，不推进业务事项；每轮只记录动作摘要、证据、缺口和用量，不要求隐藏推理。
- 按 ADR 第 7.5 节实现统一硬预算：最多 4 轮探索、8 次工具、6 次实际模型请求、累计 32,768 tokens、
  12 个片段与 12,000 字符证据、60 秒生成时限；预留最终归纳，初始读取、失败、缓存、分页和结构化修复均计账。
- 模型请求失败不自动重试，SDK 隐式重试关闭；最多一次已收到响应的结构化修复。未知用量保留预留，
  参数不合约、越权、版本变化和限额由代码拦截，不能由模型自行豁免。
- 实现 answered、needs_clarification、insufficient_evidence、budget_exhausted、no_progress、access_denied / tool_denied、
  context_changed / context_unavailable、read_failed、model_failed、interrupted 等停止原因；同消息不重启新会话。
- 额满或无进展时关闭工具，仅在剩余 / 预留预算内收尾；不足就用确定性缺口模板。输出事实、引用、
  answer_status、stop_reason、budget_usage、冲突和资料水位，不能把部分答案报为完整成功。
- 由代码生成链接并验证证据 ID / 原文片段；无依据断言还需答案忠实度评测，不能仅靠引用存在判成功。
- 新增问答提示词 / 模型与独立预算记录；保留现有 IntentResult 语义、冻结提示词和录制。
- 默认不开启普通消息的新上下文注入；接口为后续 R1 保留，后续启用需新版本对照。
- 答复发送前重新校验授权与来源状态；项目问答仅回复发起者，不调用其他成员、协调 Agent 或审批执行。

验证：目标、术语、职责、交付、状态和缺证据问题；已有探针 / 澄清时使用项目命令；
问答期间撤权；伪造引用、来源里的指令、无证据推论；普通消息与 `/同步` 回归不变。
额外逐项通过 ADR 第 7.7 节：依工具结果继续补读、提前结束、两轮无进展、各预算边界、单调计时、
模型格式修复计数、未知结果 / 崩溃、同消息重投、读期间换代 / 撤权及固定脚本轨迹重放。
在线生成未验证时，只报告结构 / 路由 / 录制结果，不声称真实模型已理解项目。

### C6：综合验收与证据分层

拟议落点：`evals/project_context/`、重启 / 网关集成测试、用户说明与开发日志。

- 冻结至少 20 项答案 / 澄清断言：目标范围、职责交付、工作记录、冲突与缺失各组均覆盖，人工核实预期事实与引用。
- 冻结不少于 12 条变化 / 失败序列，覆盖更新、重复、乱序、漏通知、A→B→A、分页、崩溃、撤权等 ADR 验收项。
- 另加不少于 12 个主动查阅循环边界样例，覆盖 ADR 第 7.7 节；至少 6 个问题需要结合规范与 Issue / PR 等不同材料。
  包含只需初始证据即可回答的对照，不用增加调用次数冒充效果提升。
- 使用固定快照和脚本 / 录制答案先验证同步、检索、引用、路由和不写业务状态；不得用 fixture 证明真实平台或模型效果。
- 循环重放记录模型结构化决策、工具参数与结果、预留 / 用量及停止原因；脚本可证明控制器遵守边界，
  不能证明真实模型会选择正确资料。真实自主选工具、缺口识别与答案忠实度另行记录实际结果。
- 若获得一个指定测试仓库的真实只读接入范围，再单独验证 App 权限、读取、Webhook、失败恢复与同步水位。
  涉及 Webhook 的事件由仓库维护者触发；OrgPilot 仍没有业务写接口。记录实际调用与覆盖，完成后停止。
- 若获得在线问答预算，按冻结问题集记录实际模型结果与人工忠实度复核，不为追求通过临时改题或扩展调用。
- 离线通过、GitHub 真实同步通过、在线答案质量通过分别记账；缺哪个证据就明确列哪个，不能合成“全部生产可用”。

## 4. 阶段验证与最终 PR 门槛

- 每阶段完成对应行为测试、必要回归和相关静态检查，通过后独立提交并继续；失败先在本阶段修复。
  C6 / 最终 PR 完成全量 pytest、覆盖率不低于 90%、Ruff、基础回放及 CI；没有新改动或未决问题时不无谓重复全量检查。
- 原意图冻结回放与已登记结果一致；新增项目问答有独立评测版本。不得重录旧结果或改 gold 掩盖行为变化。
- 生命周期保留已有 58 个通过项与唯一 D3；不能为了新功能静默改变当前 gold 或移除 D3 登记。
- 不写业务状态检查同时比较 events、OrgState、Case、审批和原待答快照；消息记录与新资料 / 问答追踪允许按设计变化。
- 每步记录新增能力、结果证据、未覆盖项和关闭 / 回滚办法，避免把接口定义或绿色单元测试当作真实接入成功。
- 两套日志均可追溯：资料修订明确自己的来源版本；现有事件重放仍不需要 GitHub、模型或网络。

建议指标：来源覆盖完成数 / 范围数、同步积压、版本收敛延迟、失效摘要命中数、错误引用数、
无依据事实数、权限隔离失败数及缺口识别结果；另记每请求探索 / 工具 / 模型次数、实际与预留 token / 费用、
无进展停止数和停止原因分布。以冻结数据的客观断言检查，不要求模型逐字复述同一答案。

## 5. 升级、关闭与停止条件

首版只新增独立表和开关，关掉项目资料同步 / 问答入口即可停止该功能；正式业务表保持原契约。
资料或权限失效、源不完整、引用不成立时，停止相关当前结论，保留可见诊断；不自动转用无来源的模型知识。
若实现发现必须改变 OrgEvent、自动推导正式任务状态、申请业务写权限或启动跨成员通知，应先报告范围变化并重新审查。

本次文档完成后停止，交给用户审查。后续用户发出整包开发指令时，按 C1–C6 连续推进，不以阶段结束为新的确认点。
仓库范围、凭据或在线预算缺失时，完成可独立推进的离线开发，将相应真实验收明确列为待完成；
必要信息一次汇总询问，已有授权不重复询问。不得将 C6 未完成的真实验收写成全部完成。
R1 仍需在本基础能力可用后独立实现和验收。

## 6. 审查后可使用的 C1–C6 连续开发指令

> 按 ADR-0015 和本计划连续实施 M2-0 的 C1–C6，包含 C4 的四类只读工具与 C5 的有界多轮主动查阅。
> 在一个功能分支按依赖顺序开发，每阶段完成对应测试、必要回归和独立提交，通过后自动继续，无需逐步确认。
> 最终完成全量测试、覆盖率、Ruff、基础回放、冻结意图回归和项目上下文 / 循环验收，准备一个可审查功能 PR，不自动合并。
> 保持单仓库只读范围，不修改正式 OrgEvent / OrgState / Case / 审批，不联系其他成员，不推进 R1、时间驱动或 GitHub 业务写入。
> 真实 GitHub / Webhook 和在线模型验收只在已有授权范围、凭据和预算明确时执行；已有授权不重复询问。
> 资源不具备时继续完成其他离线工作，将对应真实验收列为待完成，不以 Mock、录制或脚本通过替代真实能力结论。
> 最终分别汇报实现状态、阶段提交、测试结果、实际接入 / 模型证据、预算消耗与剩余限制，完成后停止。
